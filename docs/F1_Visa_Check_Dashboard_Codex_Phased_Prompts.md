# CheckMate F1 China：Codex 分阶段开发 Prompt（Demo 优先版）

## 0. 当前执行状态

- Repository：`https://github.com/UFUN0220/checkmate-f1-china`
- 阶段 0：已完成。
- 后续不得重新初始化项目、替换技术栈或覆盖阶段 0 已建立的 `AGENTS.md`、目录、依赖和文档。
- 每个阶段开始前，Codex 必须先检查仓库当前状态，以真实代码为准，而不是假设阶段 0 的具体实现。
- 当前目标不是一次建成完整平台，而是尽快做出一个可公开访问、可在同学圈扩散、能够帮助继续收集数据的可信 Demo。

## 1. 已确认的产品目标

本项目只关注中国大陆申请地点的美国 F-1 非移民签证案例，重点关注进入 Check / Administrative Processing / 221(g) 后仍在等待的样本。

Demo 服务两类用户：

1. 正处于 Check 中的学生：了解当前众包样本、查看相同地点和相似背景的案例，减少纯粹由于信息不透明造成的焦虑。
2. 准备申请美国学校或安排签证的学生：了解当前样本覆盖和等待情况，为选校、面签和入学时间安排提供参考。

Demo 的增长目标同样重要：用户看完数据后，应当自然进入“提交新案例、更新已有案例、分享当前页面”的闭环，使 80 条初始样本逐步扩展。

产品必须始终明确：

- 这是人工审核的众包数据，不是美国政府官方数据。
- 不提供法律意见，不承诺出签日期，不判断个人最终结果。
- 当前数据主要来自 Check 人群，不能计算普通 F-1 申请者“被 Check 的概率”。
- 地点百分比表示“本站已收录样本的构成”，不表示各领馆的 Check 率或风险。
- 美国使领馆服务和预约情况可能变化，实际申请安排以官方信息为准。

官方语义参考：

- Administrative Processing Information：`https://travel.state.gov/content/travel/en/us-visas/visa-information-resources/administrative-processing-information.html`
- CEAC Case Status Change：`https://travel.state.gov/content/travel/en/us-visas/visa-information-resources/visas-news-archive/visas-ceac-case-status-change.html`
- U.S. Embassy & Consulates in China Visas：`https://china.usembassy-china.org.cn/visas/`

## 3. Demo 的固定三级下钻结构

### 第一级：全国样本概览

首屏包含：

- 简洁的项目介绍。
- 当前收录案例数、仍在 Check 的案例数、数据更新时间。
- “当前样本覆盖 5 个面签地点”的说明。
- 五个地点的本站样本构成。
- “提交新案例”“更新已有案例”两个核心 CTA。

地点构成优先使用“横向分段比例条 + 五个地点卡片”。可以增加环形图，但环形图不能成为唯一导航，因为上海等小扇区在移动端难以点击。

### 第二级：地点指标

点击地点卡片后，在同一页面展开或切换该地点详情，不要求首版建立五个独立页面。

每个地点至少显示：

- 收录案例数及占全站样本比例。
- 当前仍在 Check 的案例数。
- 当前 Check 案例已经等待天数的中位数。
- 当前 Check 案例已经等待天数的平均数，可作为次要指标并同时显示中位数。
- P75 已等待天数。
- 当前最长已等待天数。
- 面签日期覆盖范围。
- Approve 数量。
- Master / PhD / Bachelor 构成。
- 专业构成。

统计命名必须区分：

- `pendingAgeDays`：仍在 Check 的案例截至数据快照日已经等待多久。
- `resolvedDurationDays`：已有可信结束日期的案例实际经历了多久。

不得把 `pendingAgeDays` 写成“处理完成时间”。只有某地点拥有足够多、完成日期明确的 resolved 案例时，才显示“已完成案例平均/中位处理时间”；否则显示“完成样本不足”。

### 第三级：人工审核后的案例记录

点击二级指标或“查看该地点全部案例”后，显示与当前地点、指标和筛选条件一致的记录列表。

用户已经允许公开以下字段：

- 地点。
- 学位。
- 专业。
- 面签月份和精确面签日期。
- 当前状态。
- Case Update。
- 学校。
- 备注。
- Initial / Renewal 等补充信息。

但公开前仍必须删除：

- 邮箱、手机号、微信号、QQ号和其他联系方式。
- 护照号、DS-160、SEVIS ID、CEAC Case Number 等身份或案件标识。
- 明确指向具体自然人的姓名或账号。
- 人工审核人员的私人信息。

因此页面应称为“人工审核后的案例记录”，而不是声称“完全未经处理的原始数据”。

## 4. 人工审核的产品定义

首版不建设复杂管理后台，继续使用现有表格和人工流程维护可信数据。

内部审核状态：

- `pending_review`：等待人工审核。
- `verified_for_publish`：格式、逻辑、重复和隐私检查通过，可以公开。
- `needs_clarification`：信息存在冲突或缺失，需要补充。
- `rejected`：明显无效、重复、恶意或无法安全公开。
- `archived`：历史记录保留但不进入当前统计。

“已人工审核”只代表：

- 字段完整性经过检查。
- 日期和状态逻辑没有明显错误。
- 重复记录已经排查。
- 联系方式和敏感信息已清理。
- 案例符合项目收录范围。

除非未来增加证据验证流程，否则不得宣传为“事实真实性已经完全验证”。公共文案建议使用：

> 案例经过人工格式、逻辑、重复和隐私检查，内容仍主要来自用户自报。

## 5. Demo 完成定义

第一版 Demo 达到以下条件即可公开扩散：

1. 用户进入首页后 30 秒内理解项目目的、样本数量和数据更新时间。
2. 用户能点击五个地点中的任意地点，看到对应二级指标。
3. 用户能点击二级指标或查看全部案例，看到正确过滤的人工审核记录。
4. 桌面端和移动端都能完成三级下钻，并能够返回上一级。
5. “提交新案例”和“更新已有案例”入口清晰可见。
6. 用户可以分享保留当前地点/筛选条件的页面链接。
7. 页面中不存在联系方式或案件标识泄漏。
8. 当前统计不被描述为普通 F-1 人群的 Check 率，也不生成具体出签预测。
9. Demo 有公开预览地址，适合在微信群、朋友圈、学校群和同学群中传播。

## 6. 通用执行规则

每个阶段都遵守：

- 开始前阅读仓库根目录 `AGENTS.md`、README、相关文档、`package.json` 和当前 Git 状态。
- 先检查现有实现，不重复阶段 0，不覆盖用户未提交修改。
- 修改尽量小而完整；不为了“最佳架构”扩大 Demo 范围。
- 每阶段必须包含 Goal、Context、Constraints、Done when。
- 每阶段运行仓库实际存在的 lint、typecheck、test、build；如果命令不存在，先说明并补最小必要配置。
- 每阶段输出简洁阶段报告，包含修改、验证、已知限制和下一阶段输入。
- 可以创建本地 Git commit；除非用户明确要求，不自动 push、创建 PR、修改腾讯文档或部署生产环境。
- 原始 Excel、审核备注和内部审核元数据不得进入前端 public 目录。
- 当前阶段只关注 F-1；不得混入 J-1、H-1B、B1/B2、OPT EAD 等不同口径数据。Renewal 仍可作为 F-1 案例属性保留。

8. 提供明确返回路径：关闭三级列表回到地点详情；清除地点回到全国概览；浏览器后退行为合理。

10. 所有图表有文本等价信息，地点卡和指标卡支持键盘操作。
11. 在 1440x900、768px 和 390x844 视口实际检查；修复溢出、截断、不可点击小扇区、图表标签重叠和返回路径问题。

Constraints
- 环形图不能是唯一地点入口。

## 阶段 8：人工审核与数据更新运营流程

```text
Demo 发布后，建立适合 80 条到数百条样本阶段的轻量人工运营流程。仍不建设复杂后台。

Goal
让新增案例能够被稳定审核、发布、更新和撤回，使 Demo 扩散后数据质量不会快速下降。

Tasks
1. 编写人工审核 checklist：F-1 范围、地点、日期、状态、重复、联系方式、案件标识、学校/备注、逻辑冲突。
2. 建立审核状态和发布批次规则。
3. 建立更新流程：
   - 导出审核后的数据；
   - 本地 dry-run；
   - schema/PII/对账；
   - 生成新快照；
   - 预览；
   - 发布；
   - 回滚。
4. 每个快照记录：asOfDate、有效样本数、地点数、状态分布、审核通过/拒绝数、数据版本，不记录审核人员私人信息。
5. 建立记录更新与删除请求流程。提交者如果要求删除公开学校、备注或整个案例，应当能够人工处理。
6. 建立重复候选规则，但不得仅凭学校+日期就自动删除；需要人工确认。
7. 创建数据运营 runbook，使非代码作者也能按步骤完成更新。
8. 记录 Demo 发布后的产品指标：新增有效案例数、更新已有案例数、地点覆盖、小样本改善。不要收集用户身份或详细筛选组合。
9. 评估何时需要数据库/后台：只有人工流程成为真实瓶颈后再提出，不提前建设。

Done when
- 使用一份复制数据完整演练新增、审核、拒绝、修改、删除和回滚。
- 敏感信息或坏 schema 会阻断发布，旧快照保持可用。
- 输出 `docs/manual-review-runbook.md`、`docs/data-release-runbook.md` 和 `docs/phase-reports/phase-8-operations.md`。
- 必要代码检查通过并创建本地 commit，不 push。
```

## 可选阶段 9：样本扩大后的高级指标

只有 Demo 已扩散并获得更多完成案例后执行。

```text
先审计新增样本，再决定是否增加完成时间、相似案例和年度趋势。不要因为页面需要更多图表而降低统计门槛。

启用条件建议：
- resolved 且有可信完成日期的案例 >= 20，才考虑全局完成时长分布。
- 单个地点 resolved 样本 >= 10，才考虑该地点完成时长中位数；平均数只作补充。
- 相似案例筛选后 n < 5 不显示定量结论，5–9 标记样本少。
- 只有获得往年同口径数据，才评估“今年是否比往年更慢”。

可选功能：
1. 含删失数据的等待完成曲线。
2. 相似案例比较器。
3. 面签周 cohort。
4. Initial 与 Renewal 分层。
5. 年度趋势与不确定性区间。

任何新增统计都必须给出样本量、公式、排除规则和误差边界，并通过测试与数据对账。
```

## 7. Demo 阶段明确不做

- 用户登录与账户系统。
- 自建管理后台。
- 自动查询个人 CEAC 状态。
- AI 预测出签日期。
- 普通 F-1 申请者的 Check 概率。
- 多签证类型混合平台。
- 评论区、论坛和私聊。
- 腾讯文档非官方抓取。
- 没有历史数据支撑的年度严重程度排名。

这些能力只有在 Demo 证明真实用户需求、人工流程成为瓶颈或数据达到统计门槛后，才进入后续评估。
